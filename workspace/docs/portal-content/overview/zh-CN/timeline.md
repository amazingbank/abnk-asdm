# 迭代时间线骨架——四层下钻导读

> 本站的核心叙事结构是四层下钻：**Sprint → Part → Phase → Task**。这一篇解释每一层的含义与阅读方式——读懂骨架，时间线页面的每一条记录都有了位置。

## 四层结构

```
Sprint（v0.0.1）            一次版本迭代——项目的时间盒
  └── Part                  交付单元——一个可独立验收的交付批次
        └── Phase           阶段——一组相关任务，带前置条件与收口判据
              └── Task      任务——最小执行单元，三件套 + 步步验收
```

| 层 | 含义 | 典型内容 | 状态标尺 |
|---|---|---|---|
| **Sprint** | 版本迭代 | v0.0.1：Fineract 核心栈起步 → 前端交付 → 工作区资产归一 → 本 portal | 进行中/完成 |
| **Part** | 交付单元 | Part01 基础起步、Part02 前端与 E2E、Part03 ASDM 工作区、Part04 Dev Portal | ⏳ → ✅ |
| **Phase** | 阶段 | 如 Part04 的数据层 → 内容层 → 站点层 → 发布层 | ⏳ → ✅ |
| **Task** | 任务 | 目的 + 改动详情 + 交付物（三件套），执行和验收步骤步步有验收 | ⏳ → ✅ |

## 任务长什么样

每个任务都是同一结构（「任务三件套」）：**目的**（为什么做）、**改动详情**（新建/修改哪些文件）、**执行和验收步骤**（每步「验证动作 → 期望输出」，实跑通过才能勾选）。任务按 ID 顺序执行，当前任务未全过不开下一任务——产出状态由验证结果驱动，不由自述驱动（这是[驾驭工程](../methodology/zh-CN/harness-engineering.md)「规约即门禁」的直接实践）。

## 怎么下钻

1. **从时间线页看全貌**：每个 Part 一段，Phase 状态与任务完成度一目了然；
2. **点进 Phase 计划**：前置条件、任务分解、已知坑——工程判断的现场；
3. **点进任务证据**：验证命令与真实输出、走查记录、截图——结论的原始依据；
4. **交叉验证**：时间线页与[指标仪表盘](../../../../index/metrics-v0.0.1.json)由生成器从同一批 front-matter 聚合，两处数字天然一致（幂等可复算）。

## 一个阅读示例

以本站自身的交付为例：[Part04 主计划](../../../Sprints/v0.0.1/part04/zh-CN/v0.0.1-Part04-Plan.md) 的进度概要表即时间线的骨架——Phase 1（数据层）已于 2026-11-16 收口，Phase 2（内容层）进行中，你正在读的这篇文档正是 Phase 2 任务 2.3 的交付物之一。**portal 展示自己的交付过程，递归叙事是设计原则。**

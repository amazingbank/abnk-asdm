# 驾驭工程——约束、验证与修复的循环机制

> 三大工程第二站：让 AI 从「会干活」到「干得对」再到「干到上线」。核心机制是把 AI 天然的小循环，一层层包进更大的工程循环——循环的半径，决定驾驭的上限。

## 定义：一句话理解 Harness

> **驾驭工程（Harness Engineering），就是构建一套使用确定性工具和方法，确保不确定性模型的确定性输出的工程体系。**

拆开看：模型本质是**不确定的**——接龙的统计特性决定了它没有绝对保证；而工程要的是**确定性输出**——可复现、可校验、可追责。中间的鸿沟靠**确定性的工具和方法**来填：工具是死的（命令、规约、脚本、状态机），方法是验证过的（循环、门禁、接力）。公式：**模型 + 驾驭层（Harness）→ 智能体**。光有大模型，得到的只是「会聊天的实习生」。

统一视角：**驾驭的本质是循环的工程化**。AI 干活的基本形态是循环——想一步、做一步、看一步结果、再想下一步。驾驭工程把这个天然小循环一层层包进更大的工程循环，让循环半径覆盖任务、交付、上线。市场上流行讲的「Harness」大多止步于第一层；**三层嵌套，才是企业级完整 Harness 体系**。

## 三层循环：半径逐层放大

### L1 · 智能体内部循环——单步会干活

**think → act → observe**：分析上下文决定下一步、调用工具执行、观察结果决定继续/修正/结束。作用范围是一个 coding session。各类 Coding Agent（Claude Code、Cursor、CodeBuddy 等）天生自带这一层，工具箱大致五组：

1. **文件五件套**：读、写、改、按名找、按内容搜——AI 的眼睛和手；
2. **Shell 入口**：一条命令通道，编译器、调试器、测试工具全从这里调用——第二层循环的关键伏笔；
3. **子代理**：派生隔离上下文的分身，并行干探查类任务，不污染主对话；
4. **技能渐进加载**：Skill 按需注入，不用不占 token；
5. **权限模式**：直接干 / 先出方案 / 只说不做，控制自治半径。

单靠这一层有三个结构性天花板：**上下文窗口有限**（一个 session 装不下整个项目）、**会话结束状态清零**（每次从零开始）、**产出质量无标准约束**（AI 说「完成了」，没有裁判）。一句话：会干活 ≠ 干得对、干得完、干到上线。

### L2 · 研发运行时循环——任务干得对

核心动作：**用 toolset 命令，把第一层的小循环编排成有状态的大循环**。以 QAHC Harness Toolset 的八条命令为例：

```
01 init → 02 askme → 03 design → 04 plan → 05 develop → 06 testplan → 07 verify → 08 review
```

每条命令被调用时做三件事：

- **注入上下文**：把项目规约、上一步产出物自动装进会话——打破「上下文有限」；
- **驱动 agent 循环**：命令内部带着 AI 跑 think→act→observe 直到该步骤完成；
- **落盘状态**：本步产出写进 workspace，交给下一条命令。

于是八条命令首尾相接：askme 的决策文档喂给 design，design 的方案喂给 plan，plan 的任务清单喂给 develop……**一个特性的交付，从「一次会话的运气」变成「八段接力的工程」**。跨会话无所谓——状态在文件里，不在对话里。

产出凭什么可信？靠两个机制：

- **规约即门禁**：每类产出物对应一份规约（质量清单）——命令驱动 AI 生成产出后，还驱动它按清单自检，不通过就进修复循环再检。这是 SDD（规约驱动开发）的落地：**先定义「对」，再生成，再校验**；
- **日志即状态机**：workspace 留下完整档案，任务状态由校验结果驱动而非 AI 自述驱动——任务可中断续跑，且 **AI 不能谎报完工**。

第二层还包括对运行时工具的调度：start.sh 一键启停、.pid 文件定位进程、logs 目录结构化日志——这些原本给人用的运维接口改造成 AI 顺手的样子，AI 就能自己跑通「改代码 → 跑起来 → 看日志 → 定位 → 再改」的循环。第二层因此不只是「写代码的循环」，而是「开发的循环」。

### L3 · DevOps 循环——干到上线自治

从 dev 到 ops，把「上线」和「上线之后」也拉进循环。传统 CI/CD pipeline 是人预先配置的固定流水线——不会思考；新形态是**以 Agent 为中心的 CI/CD**：观测 → 定位 → 修复 → 部署 → 再观测，Agent 成为流水线主体。

两个主角的组合构成 **MTTR 闭环**（Mean Time to Resolve，平均解决时长——最考验产研能力的指标）：

1. **生产定位**——观测 + 在生产环境定位根因；
2. **dev 修复**——回到开发环境用 L2 循环修掉（规约门禁保证质量）；
3. **重新部署**——带着发布前审查门重新上线；
4. **再观测**——确认修复生效，回到第 1 步。

传统模式下定位、修复、发布三个环节被组织墙和工具墙切开，MTTR 闭环从来不是真的；AI 时代，这个指标终于能被完整闭环。

## 约束-验证-修复：贯穿三层的微观机制

三层循环的每一环，内里都是同一个微观闭环——**约束**（先定义「对」：规约、清单、审查门）→ **验证**（用确定性工具检查产出：编译、测试、门禁脚本）→ **修复**（不通过就带着反馈进下一轮，直到通过才允许退出）。三层嵌套合起来：

- L1 三明治结构——想、做、查，单步内闭环；
- L2 PDCA 飞轮——命令编排接力，规约门禁，状态机持久化；
- L3 DevOps 无限环——观测、定位、修复、部署，永续运转。

**驾驭工程没有发明新循环**——三明治、PDCA、DevOps 环都是软件行业验证了几十年的老方法论；它做的是**把 AI 塞进这些循环的正确位置，然后让循环一层包一层地转起来**。

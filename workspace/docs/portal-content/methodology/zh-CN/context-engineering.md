# 上下文工程——让 AI 真正理解项目

> 三大工程第一站：知识工程的具体展开。核心问题是「怎么给 AI 供给对的上下文」——让一个每次入职都是第一天的「聪明实习生」，快速变成「懂项目的资深专家」。

## 为什么需要上下文工程

用 AI 写代码，前几轮效果不错，写到后面 AI 开始跑偏、乱改你不想动的地方——根子在两边「记忆机制」完全不同：

- **人类工程师**：有长期记忆——项目上下文自动积累，越做越熟；隐性知识持续沉淀，无需刻意管理；
- **AI 的现状**：没有长期记忆——每次对话从零开始；上下文窗口有限，塞进去的多了注意力反而稀释。

关键认知：**差距不在模型智商，而在于你是否建好了「入职材料」**。无上下文的 AI 像个聪明实习生——能力有，但不了解系统结构与命名规范，频繁产出「看起来对、放进项目就报错」的代码；有上下文的 AI 是懂业务的资深专家——产出直接融入存量代码。同一套模型，两种身份，中间隔的就是上下文工程。

## 从提示词工程到上下文工程：战术与战略

| 维度 | 提示词工程（战术） | 上下文工程（战略） |
| --- | --- | --- |
| 关注点 | 这一句 Prompt 怎么写 | 整个任务过程的信息状态管理 |
| 管理范围 | 一条消息 | 系统指令 + 工具 + 数据 + 历史 |
| 目标 | 这一次回答好 | 整个任务持续表现好 |
| 手段 | 措辞优化、few-shot | 构建结构化知识体系 |

提示词工程优化的是「单次对话质量」，上下文工程负责的是「整个任务过程的持续表现」。从战术走向战略，是从「会用 AI」到「驾驭 AI」的第一步。

上下文工程有一条精炼的定义（Anthropic 口径）：**优化传入 LLM 推理的 token 效用，以在有限注意力预算内实现预期行为**。拆开就是两个词——**高信号 token**（与当前任务直接相关、能帮 AI 做出更好决策的信息）与**噪声**（无关或冗余的信息）。要纠正一个常见误区：「上下文越多越好，反正窗口还有空间」——错。上下文充斥无关内容时，AI 对关键信息的关注度会下降。**核心不是建知识库，而是建立高效的供给机制**。

## 两条供给路径：读到，还是查到

给 AI 供给上下文，工程上有两条路径，对应两种知识形态：

### 路径一：文档型上下文（渐进式披露）

把项目知识写成结构化文档，AI 像「阅读」一样按需展开。擅长承载**意图与规范**类知识：为什么这么设计、编码规范、业务背景、架构禁区。零门槛、纯 Markdown、任何 AI 助手可用。

典型实践是**三层漏斗**架构：

- **L1 全局总览地图**（< 2KB）：项目描述、技术栈、模块入口链接——AI 每次启动的必读材料；
- **L2 领域详细地图**（< 8KB）：子模块列表、数据库表、接口清单——按任务需要动态加载；
- **Source 精准源码**：真正的代码文件——AI 根据导航定位后按需读取。

漏斗的含义是**每一层都为下一层导航**：先读 2KB 全貌，判断去哪个领域，再加载 8KB 地图，最后精准打开源码。配套三大加载策略——静态预加载（规范等稳定信息提前写好）、动态检索（有导航结构按需取用）、元数据信号（标题、标签、索引提示相关性）。三者合起来就是「渐进式披露」：**AI 不是一次获取所有信息，而是按需、分阶段地展开上下文**，token 花在刀刃上。

实测效果（QA Healthcare 官方示例项目）：同一需求，无上下文时接口返回裸 JSON、异常处理到处 try-catch；有上下文时严格用项目统一的 `Result<T>` 包装、走全局异常处理器、字段命名与存量完全一致——**有 vs 无的产出质量差距可达 3 倍以上**，而这套材料一下午就能为一个中型项目搭好。

### 路径二：图谱型上下文（知识图谱查询）

把项目知识导入本体（Ontology）图谱——前端组件、后端类与方法、数据库表，跨仓库聚合、全部对象化链接化——AI 像「查字典」一样结构化查询。擅长承载**结构与事实**类知识：谁调用谁、表与表什么关系、改动影响面。

文档型上下文有绕不开的天花板：**AI 阅读的是文本，而跨文件的结构关系埋在文本背后**。问「这个方法被谁调用了」，文本搜索大约漏掉一半调用者、带着四分之三噪音；大仓库摸底 5 万个文件要一个多小时，还可能上下文溢出、答案漂移。这不是模型不够聪明——**是让 AI 用「读小说」的方式，回答「查字典」才能回答的问题**。

真实中型项目实测（3,213 对象 / 8,077 链接，一次导入）：纯 AI Agent 读文件需要 9 文件 / 约 3 万 token 还要先搜索试错；本体 + Agent 只需 4 条查询 / 约 300 token——**上下文压缩约 100 倍**；calledBy 结构化分析把调用者遗漏率从约 50% 降为 0；快照查询约 55 秒（约 70 倍提速），且同一快照**团队答案一致**。数出来的，不是猜依赖。

### vector RAG 的位置：技术补充，不是第三条路径

行业常把「建知识库」默认等同于「上 vector RAG」——这是把技术手段当成了知识战略。两条路径的划分标准是**知识形态**（文档装意图与规范，图谱装结构与事实），向量检索不产生新的知识形态，成不了第三条路。开发场景的大多数问题是**精确型问题**（这个方法被谁调用、这个字段在哪定义），向量检索给出的是「相似」不是「事实」——top-k 既会漏也会噪，且失败是静默的。行业已付过学费：Claude Code 砍掉整条向量检索管线换回一条 grep 命令，效果反升，主流工具随后跟进。但也不必矫枉过正：**相似度型任务**（「找出和这个 bug 类似的历史缺陷」）向量检索有效，正确位置是嵌在路径一的动态检索环节——它在工具箱里，不在路径图上。

### 混合使用

- **文档型管「意图与规范」**：自然语言知识，人可读可维护，零门槛，个人和小团队今天就能起步；
- **图谱型管「结构与事实」**：结构关系一次查询精确回答，100 倍压缩、零遗漏、团队一致。

混合模式一句话：**Agent 先查字典，再读材料**——结构问题查图谱，意图问题读文档。

## 为 AI 配置工具：四段式提示词

「友好的上下文」最直接的形态是**四段式提示词**——ASDM 在真实项目中验证的受控 Vibe Coding 方法：

1. **建立上下文**：先让 AI 读取项目结构与关键文档——锁定推理空间，Agent 循环从这里启动；
2. **明确目标**：一句话指明推理方向（改进什么、达到什么状态）；
3. **约束条件**：把推理空间压缩到精确范围、规定执行步骤（不动什么、保持什么、禁止创建什么）；
4. **退出条件**：定义正确性验证（用什么命令验证编译通过、看什么日志、修复到什么程度）——这就是 Agent 循环的退出条件。

四段齐了，一次对话就能稳定拿到符合预期的结果——这就是「受控」两个字的含义。提示词只是起点；把四段式扩展为持续供给的上下文体系（规约文档、技能渐进加载、动态检索），就从战术提示词进入了战略的上下文工程。

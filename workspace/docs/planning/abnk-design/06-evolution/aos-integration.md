# AOS 集成（数据智能层）

> **性质**：设计框架（Phase 2 建立基线，Phase 5 深化）。

---

## 1. 定位与独有优势

ABNK 手上有 **AOS（ASDM Ontology Service）**——把大型 Java 仓库解析为结构化本体图谱的代码本体组件。Fineract 是 **7100 文件**的巨型仓库，正是 AOS 的目标场景。AOS 规划中已有 banking 域蓝图（`05-domains/03-banking/blueprint.md`）。

## 2. 双本体愿景

| 本体 | 对象 | 来源 | 用途 |
|---|---|---|---|
| **代码本体** | Fineract 代码结构（模块/类/调用/变更） | AOS 导入 | 定制影响分析、排障导航、升级 diff 评估 |
| **银行领域本体** | 客户/账户/交易/产品/风险 | Fineract 数据模型 + 业务 | 智能应用、跨域查询、监管映射（建法 → `domain-ontology.md`） |

两本体在"Fineract 实现了哪些领域概念"处对齐。

## 3. 分阶段路径

**Phase 2（建立基线——建议尽早，理由见下）**
1. AOS 导入 fineract 全量（7100 文件）
2. 建立初始图谱 + 基线快照
3. 首个用例：**定制影响分析**——改 custom 模块前查图谱，代替逐文件扫描

**Phase 3–4（增量与联动）**
- rebase 后图谱增量更新 → 上游变更的影响面报告（与 `release-strategy.md` 检查单联动）
- 事件总线数据进领域本体（客户/交易行为）

**Phase 5（深化）**
- 数仓 + 本体 + AI 应用（风险图谱、智能问答、异常检测）

## 4. 为什么 Phase 2 就建基线（而不是拖到 Phase 5）

1. 定制刚起步、`custom/abnk` 代码量最小——建立"干净基线"成本最低
2. 之后每次定制与每次 rebase 都增量更新，差异永远可控；拖后 = 一次性吞下全部差异
3. 影响分析立即有用（customization-strategy 的 PoC 风险管理需要它）

## 5. 依赖与风险

| 项 | 说明 |
|---|---|
| AOS 导入 7100 文件的成本 | 导入时长/资源实测待 Phase 2 评估 |
| 图谱更新与代码不同步 | 纳入 rebase 检查单（`release-strategy.md`） |
| 领域本体建模深度 | 需要银行业务专家参与（Phase 5 前不必深化） |
| AOS 侧 banking blueprint 的成熟度 | 对接前评估 |

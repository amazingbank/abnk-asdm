# ADR-004：采用 Fineract 多租户架构（分阶段落地）

- 状态：Accepted
- 日期：2026-10-25
- 决策人：ABNK 项目负责人

## 背景

Fineract 原生多租户：`fineract_tenants`（租户存储库）+ 每租户独立业务库（物理分库），按请求头路由（事实见 `00-baseline/fineract-codebase.md` §3、`environment.md` §3）。ABNK 是否使用多租户，决定了所有定制的复杂度层级：不用 → 单租户简化约 80% 定制工作；用 → 支持多法人/分行/BaaS 业务形态，但所有定制必须租户感知。

## 决策

**采用 Fineract 多租户架构。分阶段落地：**

- **阶段一（当前，Phase 1–2）**：以 `default` 单租户运行与验证——业务数据为零时多租户无从验证，不强行铺开
- **阶段二（Phase 2 起）**：建立租户生命周期管理（创建/冻结/迁移租户、租户级配置差异）
- **阶段三（Phase 3+）**：按业务需要开放多法人 / BaaS 形态

## 理由

1. **架构是现成的**：物理分库隔离、租户路由、`fineract_tenants` 元数据——启用它几乎零开发成本，弃用它反而要绕开
2. 多法人银行集团是现实业务形态，单租户架构后期改造成本远高于一开始就保持租户感知
3. 物理分库天然满足金融数据隔离合规要求

## 后果

### 正面
- 支持未来多法人/BaaS 业务形态，架构不用推倒
- 租户级数据隔离符合合规
- 多套环境（开发/测试）可以按租户切，互不污染

### 负面 / 风险与缓解
- **所有定制代码必须租户感知**：`custom/abnk` 模块的查询/缓存/批处理不得跨租户；E2E 与集成测试至少覆盖双租户场景
- 每租户独立业务库 → Liquibase 迁移按租户逐一执行，升级窗口变长 → 迁移脚本必须幂等 + 可按租户灰度
- 排障复杂度上升：定位问题先确认租户头与路由目标库
- `custom-changelog` 也会按租户执行——设计定制表时默认带租户语义（不依赖跨租户全局表）

### 必须遵守的衍生约束
- 代码与配置**不得硬编码单租户假设**（不写死 tenantId=default，不建跨租户 JOIN）
- 租户管理 API（`/v1/tenants`）在网关层的暴露策略另行设计（`02-architecture/api-gateway.md`）
- 定时作业（COB 等）的执行范围按租户明确声明

# KBank POC：ABNK 端到端演示场景方案（草案 v0.5）

> **文档目的**：与华为对齐 KBank AI Coding POC 的演示场景范围。以 Amazing Bank（ABNK）数字银行系统为背景，设计一套能够完整体现 ASDM 产品能力的端到端演示。
> **ABNK 官网**：https://amazingbank.ai
> **状态**：方案设计阶段，不含实施计划。日期：2026-10-28。

---

## 1. 演示定位

**一句话**：以一家数字银行的真实核心系统为载体，用一条真实金融需求走完「需求 → 分析 → 设计 → 开发 → 测试 → 部署 → 运营」研发全流程，展示**私有化部署**的 ASDM 方案在可信、协同、可观测三个维度上的能力。

三条价值主线：

| 主线 | 演示要证明的事 |
|---|---|
| **可信** | 私有化模型 + 企业知识供给 + 规范守卫 = 可审计、可控的 AI 编码 |
| **协同** | 数字员工以同事形态参与流程，项目知识沉淀为组织资产 |
| **可观测** | Token、任务、行为全量采集，三级看板支撑效能与成本决策 |

## 2. 演示载体：Amazing Bank

- **是什么**：基于开源核心银行系统（Apache Fineract）构建的数字银行 IT 系统——Amazing Bank，覆盖储蓄、消费贷款、账务、日终批处理等真实银行业务。
- **规模**：约 145 万行代码（其中手写 Java 约 92 万行），603 个业务 API 端点，自带 200 个官方端到端业务测试。
- **为什么可信**：真实服役十余年的银行核心，不是演示专用的玩具代码库；全部测试资产可直接复用为演示的回归基线。
- **对 POC 的意义**：同时支撑「复杂工程——百万行级代码库上的影响分析」与「简单工程——全流程交付」两类演示需要；储蓄、贷款、账务等核心银行业务为演示提供真实的金融场景底座。

## 3. 演示故事设定

**业务需求**（一条主线贯穿全场）：

> 监管要求：客户身份证件过期后，银行必须拦截其新交易。Amazing Bank 需要在核心系统上新增「客户证照过期拦截」特性，并保证不破坏既有储蓄、贷款业务链路。

选择这个需求的理由：
1. **合规驱动**——银行背景听众秒懂，价值无需解释；
2. **触及核心**——需要改动核心客户域，影响面横跨储蓄、贷款、账务多个模块，影响分析有深度、有戏可演；
3. **风险真实**——在核心银行系统上动刀，「漏改一处」就是生产事故，客户痛点最强。

## 4. 演示主线：研发全流程分阶段细化

> 每个阶段回答四个问题：做什么、银行业务价值是什么、体现什么能力、解决什么问题。全程运行在华为 OpenLab 昇腾 950 设备 + 开源大模型之上，代码与数据不出域。

### 阶段总览

| # | 阶段 | 主演能力 | 一句话看点 |
|---|---|---|---|
| 0 | 私有化底座 | 全家桶 | 一屏看清私有化环境全景与企业身份接入 |
| 1 | 需求受理 | aLink 数字员工 | 需求自动进入流程，数字员工主动认领 |
| 2 | 影响分析 | 知识引擎 | **全场爆点：有/无知识图谱的 A/B 对比** |
| 3 | 方案设计 | 知识引擎 + 数字员工 | 有据可依的设计文档与评审 |
| 4 | 编码执行 | aLink 运行时 | 多引擎编码 Agent 受控执行、红线守卫 |
| 5 | 测试回归 | 治理平台 | 200 个存量业务测试的自动回归门禁 |
| 6 | 部署与运营 | 治理平台 | Token 成本、任务级行为的可观测看板 |
| 7 | 知识回流 | 知识引擎 + 资源中心 | 新增代码反哺知识库，组织记忆生长 |

### 阶段 0：私有化底座（开场）

| 维度 | 内容 |
|---|---|
| 做什么 | 展示部署在 OpenLab 昇腾 950 上的完整环境：开源大模型推理服务 + ASDM 全套平台；演示人员以企业账号统一登录（SSO），展示组织、项目、成员与权限层级 |
| 业务价值 | 证明「全套私有化、代码与数据不出域」不是承诺而是现状；多工具并存收敛为一个受治理的统一入口 |
| 对应能力 | ASDM 统一治理平台（组织身份、权限、多租户）；昇腾 950 + 开源大模型推理 |
| 解决问题 | 代码与数据不出域；多工具并存收敛为统一治理入口；企业身份体系统一接入 |

### 阶段 1：需求受理与任务分发

| 维度 | 内容 |
|---|---|
| 做什么 | 监管需求录入研发管理系统成为工作项；数字员工（aLink）自动认领任务、拆解子任务、生成初步执行计划，并在关键节点主动向负责人汇报进展 |
| 业务价值 | 需求从「合规条文」到「研发任务」的转译零人工；合规需求全程可追溯——谁认领、做了什么、结论如何，全部留痕 |
| 对应能力 | aLink 数字员工（任务认领、主动汇报、优先级收件箱）；治理平台与 DevOps 流程集成 |
| 解决问题 | 团队级 AI 协作范式：AI 不是旁挂工具，而是流程内承担明确职责的「同事」 |

### 阶段 2：影响分析（**核心爆点：A/B 对比**）

| 维度 | 内容 |
|---|---|
| 做什么 | 同一个需求、同一个模型、同一份提示词，只变一个变量——**是否有知识图谱供给上下文**：<br>· **B 组（常规方式）**：AI 直接在 145 万行代码库里自行探索，耗时数分钟、反复试错、上下文塞满 token，结论有遗漏<br>· **A 组（知识工程方式）**：AI 查询预先构建的代码知识图谱，秒级返回精确影响面清单（涉及的模块、数据库表、API 端点、既有测试用例），并输出可审计的影响分析报告 |
| 业务价值 | 银行核心系统最怕「改一处、崩一片」——影响分析从依赖资深工程师的记忆，变成分钟级、可复核的机器产出；新人/外包团队也能安全地在核心系统上作业 |
| 对应能力 | ASDM 知识引擎（代码知识图谱：对象、链接、动作三原语；确定性查询，不依赖大模型） |
| 解决问题 | 百万行级存量代码库的影响面黑盒——从依赖资深工程师的记忆，变成人人可复核的图谱查询；同时展示私有化模型配上好的知识供给所能达到的效果上限 |

### 阶段 3：方案设计

| 维度 | 内容 |
|---|---|
| 做什么 | 数字员工基于影响分析结果生成技术方案（改哪里、怎么改、如何验证），关键设计决策附代码级依据；人类专家评审修订，评审记录与方案一并归档为项目知识资产 |
| 业务价值 | 设计文档从「拍脑袋」变成「有据可查」；评审聚焦在决策而非细节核对；方案沉淀后可被后续相似需求复用 |
| 对应能力 | 知识引擎（精确上下文供给）；aLink 数字员工（方案生成）；资源中心（方案归档与复用） |
| 解决问题 | 组织级记忆：资深工程师的设计经验不再锁在个人脑中，项目知识成为可传承的组织资产 |

### 阶段 4：编码执行

| 维度 | 内容 |
|---|---|
| 做什么 | 数字员工在受控运行环境中执行编码：每个任务在独立隔离的容器内运行，按需切换编码引擎（OpenCode 为主，华为近期开源的 iCode 作为备选——接入可行性待验证），企业规范（如「核心账务引擎禁止修改」红线）作为守卫规则实时拦截违规改动 |
| 业务价值 | 效率提升的同时守住银行底线——AI 生成的每一行代码可追溯到任务、遵循红线、经过门禁；多引擎按任务选择，不被单一厂商锁定 |
| 对应能力 | aLink 运行时（守护进程 + 容器化隔离执行 + 多引擎接入）；治理平台（规范与守卫规则管理） |
| 解决问题 | AI 生成代码的可信与可控；多引擎按任务选择、不被单一厂商锁定；执行环境安全隔离 |

### 阶段 5：测试与质量门禁

| 维度 | 内容 |
|---|---|
| 做什么 | 新特性开发完成后自动触发回归：跑 Amazing Bank 既有的 200 个官方端到端业务测试 + 新特性自动生成的单元/集成测试；覆盖率与通过率作为质量门禁，不达标不放行 |
| 业务价值 | 核心银行系统的每一次变更都有全量业务回归兜底——这是银行敢于让 AI 写代码的底气；回归时间从人工周级到机器小时级 |
| 对应能力 | 治理平台（流水线编排、质量门禁）；数字员工（测试用例生成） |
| 解决问题 | 「AI 写的代码敢不敢上生产」——用存量测试资产回答，而不是用承诺回答 |

### 阶段 6：部署与运营

| 维度 | 内容 |
|---|---|
| 做什么 | 特性通过门禁后部署，演示运营视角：全员 AI 使用看板——Token 消耗（按团队/按引擎/按任务维度）、效率指标（采纳率、任务完成率）、成本趋势；A/B 两组的数据在同一看板对比呈现 |
| 业务价值 | AI 投入产出从「感觉有效」变成「数据可见」；为明年 AI 预算申报和工具采购评估提供量化依据 |
| 对应能力 | 治理平台（全链路遥测、三级看板） |
| 解决问题 | Token 成本与 AI 效能从不可见到可见——为 AI 投入的预算与采购决策提供数据依据 |

### 阶段 7：知识回流（收尾闭环）

| 维度 | 内容 |
|---|---|
| 做什么 | 本次交付的新代码增量更新进知识图谱；过程中踩的坑、形成的做法沉淀为最佳实践发布到资源中心，团队其他成员「一行命令」安装复用 |
| 业务价值 | 每做一个需求，组织就变聪明一分——AI 能力随项目演进持续进化，而不是每次从零开始 |
| 对应能力 | 知识引擎（增量更新）；资源中心（实践发布、一键安装、贡献排行） |
| 解决问题 | 组织级记忆与知识复利；AI 越用越好，而不是越用越贵 |

## 5. 深化场景（已选定 A + B 两个，对齐「本体工程、知识工程重点测试」）

| 场景 | 内容 | 亮点 | 状态 |
|---|---|---|---|
| **A. 深调用链影响分析** | 选取贷款还款处理这类横跨多模块的深业务链路，做知识图谱驱动的全链路影响分析，与人工方式对比 | 复杂工程用例的直接落地 | ✅ **已选** |
| **B. 系统升级影响评估** | 上游开源核心发布新版本 → 图谱自动对比新旧版本差异 → 输出「本次升级影响 Amazing Bank 哪些定制」的评估报告 | 竞品几乎没有的能力；天然体现知识库随项目演进的长期价值 | ✅ **已选** |
| C. 监管报送概念映射 | 监管报送字段与系统数据概念的自动映射 | 银行味最浓 | ❌ 不做——数据链路尚未成熟，演示需造数据，影响「实测而非 PPT」的可信叙事 |

## 6. 环境与交付形态

- **环境**：华为马来 OpenLab 昇腾 950 设两台，部署开源大模型推理服务 + ASDM 全套平台 + Amazing Bank 系统；软通远程登录完成部署与联调。
- **工具**：AI Coding 工具按会议建议采用 OpenCode 为主（已验证可接入 aLink 运行时），华为近期开源的 iCode 作为备选。iCode 宣称支持标准 Agent 协议与本地模型部署，但其接入 aLink 运行时的可行性**当前尚未验证**，将在 POC 准备期验证后再确认是否纳入演示；引入 iCode 亦为华为+软通联合方案的生态呼应点，具体选型可在 POC 启动前与华为共同确认。
- **节奏**：远程完成环境搭建与演示彩排；POC 交付节点由软通专家到客户现场组织 workshop 演示与交流。
- **数据**：演示用种子数据（含过期证照客户、逾期贷款等业务数据）提前准备。

## 7. 范围边界（明确不做的事）

1. **不在客户现场、基于客户环境/代码做任何人天投入**（对齐既定共识）；
2. 演示场景将**首先基于公网大模型构建**（首选 GLM 5.3 或其最新版本），作为场景设计与彩排的基础；
3. 在昇腾 950 私有化部署模型上运行时**可能出现效果衰减**——将根据实测情况对演示场景做相应裁剪，并对最终呈现效果建立合理预期（现场演示的模型推理均在昇腾设备本地完成）；
4. 不承诺与公有云闭源模型的同口径性能对比——演示重点是「知识供给 + 治理」带来的差异，而非模型本身；
5. 本 POC 不包含生产级安全加固、高可用部署等企业化实施内容。

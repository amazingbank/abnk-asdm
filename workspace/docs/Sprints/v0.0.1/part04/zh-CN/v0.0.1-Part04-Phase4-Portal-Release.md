### 已知环境坑

1. **服务端构建铁律**（D8 铁律 2）：本地 Mac 构建的镜像不推送不发布（仅调试）——4.1 本地验证止于「容器跑通 + curl 200」，镜像发布在服务器侧执行（4.2）。
2. **禁止覆盖已推送 tag**（D8）：tag 用时间戳或递增版本；回滚靠拉历史 tag。
3. **PAT/凭证边界**（ADR-010 + prod-deploy）：凭证只存 `.github-private` 与服务器 docker config——文档/证据/发布记录不得出现凭证内容（路径引用允许）；registry 以 FQN 记录。
4. **子域接入现有拓扑**：dev 子域以新 server 块接入既有 abnk-nginx 反代（api/app/bo 模式第四次适用）——不得另起端口或绕过统一入口。
5. **数据新鲜度如实**：发布是手动链——页脚如实标注「数据截至 index 最后 commit」（D6 诚实性在发布层的体现）；CI 自动化属 roadmap 不虚标。
6. **官网 CTA 跨仓纪律**：abnk-website 是 private 独立仓——改动走该仓正常流程；改动量限「两板块各加一链接 + 一句文案」，勿顺手改其它内容。
7. **服务器侧两仓获取形态**：服务器构建需 abnk-asdm + abnk-devportal 两仓可达——实际形态（服务器 clone 只读或其它）在 4.2 执行时定死并写入 4.4 手册，不留模糊口径。

## 背景与动机

Phase 3 产物只能本地 preview；「dev portal 上线」在本 Phase 完成——容器化复刻 website 成熟先例（低风险）、部署走既有铁律与子域拓扑（第四次适用）、官网入口完成流量闭环、发布手册固化手动链（CI 未实跑期间的可复现性保障）。上线时点同时是叙事闭环时点：portal 展示的最新内容 = Part03/Part04 自己的交付全过程。

## 方案要点

1. **容器化照先例**：多阶段构建（node:22 build → nginx:alpine 直供 dist）+ nginx.conf 复刻 website（SPA fallback + `/evidence/` 资产缓存头 + gzip）；纯静态零 env 注入（locale 走运行时 UI 切换）。
2. **发布走铁律**：本地容器验证（4.1）→ 服务器侧构建 + ghcr push（4.2，禁止覆盖 tag）→ dev 子域接入既有反代 → 两阶段发布 + 用户确认。
3. **CTA 最小化**：官网 Asdm/OpenSource 板块各加一个 dev.amazingbank.ai 链接。
4. **手册 = 实际链路固化**：4.4 记录实际执行过的命令链（含服务器侧两仓获取形态），CI 落地前的唯一发布事实源。

**执行规则（全任务生效）**：

1. 步骤必须实际执行并记录真实输出；生产侧步骤全步骤执行前过用户确认铁门。
